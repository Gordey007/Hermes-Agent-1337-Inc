# 07 — Hermes-kanban (built-in tool)

Kanban is a **native Hermes Agent tool**, not our implementation. It's a durable task board in the shared database `~/.hermes/kanban.db`, shared by all profiles. The sprint team coordinates through it, and a person sees every step in the dashboard.

Docs: <https://hermes-agent.nousresearch.com/docs/user-guide/features/kanban>,
worker lanes: <https://hermes-agent.nousresearch.com/docs/user-guide/features/kanban-worker-lanes>,
tutorial: <https://hermes-agent.nousresearch.com/docs/user-guide/features/kanban-tutorial>.

## Two access surfaces
- **Agent** — via tool-calls (built into the profile's schema): `kanban_show`, `kanban_list`, `kanban_create`, `kanban_link`, `kanban_comment`, `kanban_complete`, `kanban_block`, `kanban_heartbeat`.
- **Person** — the `hermes kanban ...` CLI and the dashboard (`hermes dashboard` → http://127.0.0.1:9119).

Both surfaces hit the same `kanban.db`.

## Columns / statuses (native)
```
Triage ──▶ Todo ──▶ Ready ──▶ Running ──▶ Done ──▶ Archived
                                   └──▶ Blocked
```
- `kanban_complete()` — the only "successful" way to close a claim (structured handoff: summary + metadata).
- `kanban_block()` — pause, escalate to a person (for code edits — prefix `review-required:`).
- A worker exiting without a tool-call → failure handling.

## Worker lanes (how work is delegated)
- A lane = a process class to which the dispatcher routes a task. Routing — by the `task.assignee` field.
- `assignee` = the **name of a Hermes profile** (`orchestrator_sprint`, `researcher`, `architect`, `developer`, `tester`, `evaluator`, `sales`) or a registered plugin lane.
- If the assignee does not resolve — the task stays in `ready` with a `skipped_nonspawnable` event (it isn't lost).
- The **dispatcher** is started with `hermes gateway start`: it periodically pulls tasks of all profiles from the single `kanban.db` and spawns workers for the right profile. This replaces "fragile in-process sub-agent swarms" — delegation goes through lanes, not only through `delegate_task`.

## Orchestration
- The orchestrator profile (`kanban.orchestrator_profile` in the config) receives the parent task and judges completion when the dependencies are closed.
- Decomposition: `kanban_create` (child) + `kanban_link` (parent→child), then the orchestrator "steps back".
- Auto mode — the built-in decomposer splits the triage task by role on its own (`hermes kanban decompose <id>`, or the Auto/Manual toggle in the dashboard).

## Our naming on top of native kanban
- The **task title** carries our id for monitoring: `hab-<tweetid>-s<sprint>-<role>-<seq>` (generated by `infra/naming.py`).
- **`--assignee`** = the name of the executor profile; **`--tenant`** = `hab_<tweetid>` (grouping by lead).
- **`--parent`** = the sprint's root task.
- Artifact handoff — in `kanban_complete(summary, metadata={artifact: <path|minio-key>})` and/or `kanban_comment`.

## Iteration counters (which kanban doesn't have natively)
The limits (`dev_architect ≤5`, `architect_researcher ≤5`, `github_search ≤10`, `inner_loop ≤10`, `outer_loop ≤10`) aren't counted by kanban itself. We keep them in a lightweight sidecar `04_team/kanban/counters.py` (`COUNTERS_DB_PATH`), key = `(tweet_id, sprint, counter)`. We duplicate the value into a `kanban_comment` so a person can see it in the task thread.

## Wrapper skills
- `_shared/kanban-read` — `kanban_list`/`kanban_show` (own/parent tasks).
- `_shared/kanban-write` — `kanban_create`/`kanban_link`/`kanban_comment`/`kanban_complete`/`kanban_block` + increment the sidecar counter.

## Lifecycle of a sprint task
`orchestrator_global` (`og-start-sprint`) creates the root task (`--assignee orchestrator_sprint`, `--tenant hab_<tweetid>`). `orchestrator_sprint` (`os-plan-sprint`) uses `kanban_create`+`kanban_link` to create phase child-tasks (research→design→dev→test→eval) for the executor profiles. The dispatcher (`hermes gateway`) spawns workers. Once the dependencies are closed, the orchestrator sums up in the parent task.
